# DF Main/Rod 통합 펌웨어 리팩토링 로드맵

Updated: 2026-09-09

현재 로컬 `main`은 실패한 IMU 게임 좌우 보정 연구를 제거한 `8b2fd4f`다. 실패 연구는 `codex/imu-calibration-experiment-failed`에 보관하며 로드맵의 활성 작업으로 취급하지 않는다. 활성 구현 잔여 작업은 0개이고, 사용자 지시 전에는 새 작업을 시작하지 않는다.

## 목표

`Vm1.0.9.0` Main 펌웨어와 `Vr1.0.1.0` Rod 펌웨어를 하나의 저장소, 빌드 기준, 프로토콜 계약, 작업 관리 및 릴리스 체계에서 관리한다. 두 펌웨어는 독립 바이너리로 유지하되 현재 사용하는 하드웨어와 기능만 남기고, 대규모 `.ino`를 C++98/03 호환 `.cpp/.h` 모듈로 단계적으로 분리한다.

```text
DF Firmware Repository
├─ Main Firmware ─┐
│                 ├─ DF Protocol Contract ── Manual Main/Rod Integration Test
└─ Rod Firmware ──┘
```

## 최신 요청 처리 (2026-08-31)

사용자 명시적 묶음 요청으로 작업 10-I/J를 추가했다. HANDLE 시험 LED를 제거한 `Vr1.0.1.3` build/protocol test, USB 고속 직접 업로드·flash verify·재부팅 버전 확인과 140장 소스 인수인계 PowerPoint를 완료했다. 복구 후 물리 LED 확인은 사용자 대기다. 작업 10-H 및 기존 검증 게이트는 미완료로 유지하며 잔여 번호 작업은 4개(01, 08, 09, 10), 작업 10 잔여 문자는 H 1개다.

2026-08-31 추가 사용자 요청으로 02-H 출력 버전 동기화를 보완했다. Version.cpp만 수정하면 build/clean 경로가 자동으로 따라간다. Main `Vm1.0.10.0`, Rod `Vr1.0.2.0` 통합 빌드 및 각 새 버전 폴더 4파일을 확인했다. 업로드는 수행하지 않았고 기존 잔여 작업 수는 동일하다.




2026-08-31 BLDC 건은 사용자가 최신 코드가 옳다고 확인하여 03-I 해결 완료 처리했다. PWM 반전 최신 코드는 유지하고 추가 분석 및 미해결 기록을 제거했다. 완료 근거는 사용자 확인이며 Codex의 새 빌드·테스트·업로드는 없다. 잔여 번호 작업은 기존 4개(01, 08, 09, 10)다.

2026-09-01 작업 11-A~H에서 testModule 독립 프로젝트와 합의한 UI, 시리얼/장비 명령, ZIP firmware update를 구현했다. 단일 EXE 게시와 자체 검사까지 완료했으며 실제 장비 gate인 11-I만 대기한다. 기존 잔여 작업은 보류 상태로 유지하며 잔여 번호 작업은 5개(01, 08, 09, 10, 11)다.

2026-09-01 MAIN 업데이트는 불완전 설치 상태도 복구할 수 있도록 내장 esptool 기반 ROM 직접 기록으로 변경했다. update.bat 기준 네 flash 영역과 921600bps를 사용하며 일반 시리얼 115200bps는 유지한다. build/self-test는 완료했고 실제 장비 gate 11-I는 유지한다.

2026-09-01 후속으로 MAIN의 복구 표기를 제거하고 ROD 유선도 동일한 내장 esptool 네 영역 기록으로 통일했다. $1800%는 MAIN의 AP 종료 요청으로 정정해 TestModule이 수신을 표시하고 한 번 응답하도록 했다. 실제 ROD 장비 gate는 대기한다.

2026-09-01 업데이트 직후 첫 연결 상태 누락은 초기 명령 연속 송신으로 확인했다. 레거시의 500ms 3단계 초기화와 단계 내부 60ms 간격을 적용하고 초기화 완료 후 polling을 시작한다. 실제 장비 재검증은 대기한다.
2026-09-01 제공 로그 재분석으로 포트 오픈 전 수신 backlog와 잘못된 $1800% 자동 ACK도 확인했다. 연결 시 버퍼와 decoder를 초기화하고 자동 ACK를 제거했으며, ROD/IMU 상태 확인 뒤 버전을 한 번 조회하도록 순서를 보완했다. Release build/self-test는 완료했고 11-I 실제 장비 gate는 유지한다.



2026-09-02 사용자 지시로 수행 범위를 `LM JIG 실제 제어`와 `무선 업데이트 보완`으로 한정했다. 기존 01/08/09/10-H/11-I 검증·마감 항목은 활성 잔여 작업에서 제외하며 과거 기록만 보존한다. 작업 11-J 이후 11-K 순으로 수행했고 두 작업을 모두 완료했다.

2026-09-02 작업 11-J에서 무선 시작 경고를 제거하고 완료 즉시 MAIN polling 복구, 최대 12초 ROD 재연결 확인, 버전 조회 및 결과 팝업을 구현했다. 현재 96-byte/ACK protocol은 기존 설치 firmware 호환 범위의 최대치로 유지했다.

2026-09-02 작업 11-K에서 런타임 LM JIG 판별, LM 핀·PWM, `$07` 직접/위치 제어와 센서/3초 안전 정지를 복구했다. MAIN/TestModule build와 TestModule self-test를 완료했으며 활성 구현 잔여 작업은 0개다. 플래시와 장비 시험은 수행하지 않았다.

## 진행 순서

01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10 → 11

사용자 요청으로 작업 08/09의 잔여 검증을 보존한 채 작업 10을 먼저 활성화한다. 작업 10의 장비 gate 결과는 작업 09 통합 검증에도 재사용할 수 있다.

작업 05와 06은 작업 04 완료 후 순서를 바꿀 수 있으나 동시에 대규모 변경하지 않는다.

작업 01-F와 작업 02-F는 같은 Main/Rod clean build 결과를 사용한다. VS2022 솔루션에서 최초 빌드하기 위해 작업 02 A–E를 작업 01의 장비 확인 B/C/G보다 먼저 진행할 수 있다.

2026-08-27 사용자가 작업 03~06을 하나의 묶음으로 명시하고 build/검증/test 생략을 요청해 구현을 연속 수행했다. 각 작업의 검증 게이트는 성공으로 간주하지 않고 미수행 상태로 기록한다. 이 결과는 `.ino` 축소와 기능 경계 분리까지의 1차 초안이며 `.inc`가 독립 `.cpp/.h`로 정착한 최종 구조가 아니다.

작업 07에서는 코드 변경 전에 `docs/refactoring/SOURCE_REFACTORING_DRAFT.md`를 기준으로 전역 의존성, 상태 owner, 공개 API와 전환 순서를 먼저 확정한다. 실제 `.inc` 제거와 안전성 변경은 작업 08에서 한 문자 단위로 수행하고 검증한다.

## 운영 규칙

- 한 번에 한 번호 작업서만 활성화한다.
- 작업서 안에서도 한 번에 한 문자 단위만 처리한다.
- 코드 변경과 동작 변경을 같은 문자 작업에 섞지 않는다.
- compile/link 빌드는 Codex가 직접 실행하고 결과를 기록한다.
- 플래시 또는 장비 검증 게이트에 도달하면 Codex는 중단하고 사용자에게 필요한 실행 내용과 결과 항목을 알린다.
- 사용자 결과를 받기 전에는 플래시 및 smoke/HIL 검증을 완료로 기록하지 않는다.
- 제거 코드는 먼저 `deprecated/`에 출처와 제거 이유를 기록한 뒤 활성 코드에서 제거한다.

## 공통 변경 금지 경계

- 현재 Main/Rod 메시지 PID, payload 형식, 타이밍 및 장비 동작을 의도 없이 변경하지 않는다.
- `Vm1.0.9.0`과 `Vr1.0.1.0` 기준 원본을 덮어쓰지 않는다.
- C++11 이후 문법, 람다, 스마트 포인터 및 namespace를 도입하지 않는다.
- 과거 Variant를 활성 빌드 경로에 다시 도입하지 않는다.
- ESP32 Arduino Core는 기준선 확인 전 2.0.17에서 임의 업그레이드하지 않는다.
- 사용자의 명시적 요청 없이 commit, push, flash 또는 장비 제어를 하지 않는다.
